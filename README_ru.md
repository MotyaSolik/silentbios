# SilentBIOS

Вайбкод хрень by Claude

Самодельный минимальный BIOS для x86 (16-бит real mode), написанный с нуля на
NASM-ассемблере. Занимает ровно 64 КБ и размещается как обычный legacy BIOS
ROM-образ — reset vector в конце файла делает `jmp` на точку входа, как на
настоящей материнской плате.

Собирался и проверялся в QEMU (`qemu-system-i386`) на каждом шаге — не
просто "компилируется", а реально гонялся с осмотром serial-вывода и
скриншотов VGA-экрана.

## Возможности

- **Вывод по COM1** (9600 8N1) — простейший, но независимый от видео канал
  диагностики.
- **VGA text mode 80×25**, настроенный полностью вручную через порты
  контроллера (Sequencer, CRTC, Graphics Controller, Attribute Controller,
  DAC-палитра) — без какой-либо видео-BIOS/option ROM. Растровый шрифт 8×16
  сгенерирован и зашит отдельным бинарником (`font.bin`, подключается через
  `incbin`). Вывод за последней строкой прокручивает экран вверх, а не
  утекает за пределы видимого буфера.
- **POST-диагностика**: тест conventional-памяти (0–640 КБ, блоками по 64 КБ)
  и самотест контроллера клавиатуры 8042 (команда `0xAA`).
- **Интерактивное setup-меню** — стрелки/Enter/Esc, опрос клавиатуры прямым
  поллингом портов `0x60`/`0x64` (Scan Code Set 1 — контроллер сам
  транслирует его из нативного Set 2, как и настоящий BIOS). Тумблеры
  Serial/VGA output реально встроены в вывод, а не просто рисуются.
- **CMOS/NVRAM** — настройки тумблеров сохраняются в CMOS (порты `0x70`/
  `0x71`) и переживают аппаратный reset, как на настоящей материнке с
  батарейкой.
- **Загрузка с диска** — чтение MBR (сектор LBA0) напрямую с первичного ATA-
  контроллера в режиме PIO (порты `0x1F0`–`0x1F7`), проверка сигнатуры
  `0x55AA` и передача управления по адресу `0000:7C00` с регистрами,
  выставленными как у настоящего BIOS (`DS=ES=SS=0`, `SP=0x7C00`,
  `DL=0x80`).
- **`int 10h`** — настоящий обработчик программного прерывания, прописанный
  в IVT. Загруженный код/ОС может просто вызывать `int 10h`, как в настоящем
  BIOS, вместо прямого доступа к видеопамяти/портам. Поддержанные функции:
  `AH=0x0E` (teletype output), `AH=0x00` (смена режима — только `0x03`),
  `AH=0x02`/`0x03` (установка/чтение позиции курсора, включая настоящий
  аппаратный курсор CRTC через порты `0x3D4`/`0x3D5`), `AH=0x0F` (чтение
  режима), `AH=0x09` (запись символа с атрибутом без сдвига курсора —
  добавлена, потому что именно ею GRUB рисует цветную рамку меню; без
  неё GRUB работал, но ничего не рисовал).
- **`int 16h`** (клавиатурные сервисы) — декодирует тот же поллинг Scan
  Set 1, что и setup-меню, в ASCII, с поддержкой Shift. `AH=0x00` читает
  символ (блокирующе), `AH=0x01` проверяет наличие клавиши, не потребляя
  её (неблокирующе, результат через `ZF`). Numpad, функциональные и
  прочие не-ASCII клавиши тихо игнорируются. Скан-код в `AH` — тот же
  Set 1, что уже пришёл с порта (раньше, пока контроллер отдавал сырой
  Set 2, здесь была отдельная программная трансляция — убрана, когда
  включили аппаратную, см. "Известные ограничения").
- **`int 13h`** (дисковые сервисы) — загруженный загрузчик/ОС может читать
  диск, не разговаривая с ATA-контроллером напрямую. `AH=0x00` (сброс),
  `AH=0x02` (чтение секторов, CHS — транслируется в LBA28 по условной
  геометрии, т.к. `IDENTIFY DEVICE` не реализован), `AH=0x08` (параметры
  диска). Геометрия зависит от номера диска: `DL<0x80` (floppy) →
  `18 секторов/дорожка, 2 головки` (стандарт 1.44MB), `DL>=0x80` (HDD) →
  `63/16` — найдено эмпирически, попыткой загрузить настоящую дискету
  FreeDOS и временным serial-логом каждого вызова `int 13h`, чтобы
  увидеть, какие именно CHS запрашивает её загрузочный сектор. Об
  ошибках сообщает честно: неподдерживаемая функция возвращает
  `CF=1`/`AH=1`, а не тихо притворяется, что всё прошло успешно — для
  дисковых операций так безопаснее, чем для видео/клавиатуры.
- **`int 12h`** (объём conventional-памяти) и **`int 15h` `AH=0x88`**
  (объём расширенной памяти). `int 12h` возвращает то, что реально
  измерил `post_memory_test` при POST (0-640KB). `int 15h AH=0x88`
  берёт ответ прямо из стандартных CMOS-ячеек `0x17`/`0x18` (расширенная
  память в KB), которые заполняет сама платформа — как настоящее
  железо, так и QEMU; сами память выше 1MB мы не пробуем (нет
  A20-gate/unreal mode). Прочие функции `int 15h` возвращают
  `CF=1`/`AH=0x86` ("функция не поддерживается") — тот же код, что и у
  настоящего BIOS в этом случае.

## Запускает GRUB

Настоящая установка GRUB — MBR-таблица разделов, раздел FAT32,
`grub-install --target=i386-pc` — грузится до настоящего цветного меню
GRUB на этой BIOS, на реальном железе, не только в QEMU. (Более ранняя
попытка с ISO9660-образом от `grub-mkrescue` доходила только до
запасного `grub rescue>` с ошибкой "unknown filesystem" — особенность
скармливания CD-раскладки как сырого диска, не ограничение BIOS;
нормально размеченный образ диска в это не упирается.)

К этому результату привели четыре находки, каждая — по чтению точного
текста ошибки, а не угадыванием: разделение геометрии floppy/HDD у
`int 13h`, `int 10h AH=0x09` для рамки меню GRUB, настоящие числа в
`int 15h AH=0x88` вместо честного нуля, и — найдено только когда
реальный пользователь попробовал на реальном железе — перевод скан-кодов
клавиатуры из Set 2 в Set 1 перед тем, как отдавать их в `AH` у
`int 16h`. Последнее оказалось важным потому, что GRUB доверяет `AL`
(ASCII) для обычного набора текста, но распознаёт спецклавиши вроде
Enter по `AH` (скан-код) — буквы заработали задолго до того, как
заработал Enter.

Пятый пробел нашёлся, когда копнули ещё дальше: `int 13h` всегда
разговаривал с *master*-диском на primary-канале, независимо от того,
что просили в `DL` — поэтому GRUB, перебирающая много возможных номеров
BIOS-дисков в поисках своего, видела один и тот же физический диск под
десятком разных имён, а второй подключённый диск (`-hdb` в QEMU) был
недостижим ни под каким номером. Теперь `int 13h AH=0x02` выставляет
бит выбора диска в порту `0x1F6` по `DL` (`0x80`/`DL<0x80` → master,
`0x81` → slave — второй диск на ТОМ ЖЕ primary-канале, соответствует
`-hda`/`-hdb` в QEMU). Проверено двумя подключёнными дисками с разным
известным содержимым в LBA0, прочитанным по очереди через разные `DL`.

Одного этого оказалось мало — `ls` в GRUB всё равно показывал десяток с
лишним фантомных дисков, потому что ЛЮБАЯ функция `int 13h` отвечала
"успех" на любой `DL`, master/slave или нет — номера дисков, которых мы
не поддерживаем, выглядели точно так же "существующими", как настоящие
два. Теперь `int13h_isr` проверяет `DL` ещё до диспетчеризации по
функции: только `DL<0x82` (floppy, master или slave) получают
настоящий ответ; всё остальное — secondary ATA-канал, не реализованный
в этом проекте — честно возвращает `CF=1` ("такого диска нет"), тем же
способом, каким настоящий BIOS сигнализирует об этом при переборе.

## Структура файлов

| Файл             | Назначение                                                        |
|-------------------|--------------------------------------------------------------------|
| `bios.asm`        | Исходник BIOS                                                      |
| `font.bin`        | Растровый шрифт 8×16 (256 символов × 16 байт), подключается через `incbin` |
| `sbios.bin`       | Готовый собранный образ, 65536 байт                                |
| `boot.asm` / `boot.bin` | Тестовый диск, stage 1: сектор MBR. Минимальный загрузчик — печатает строку, читает `stage2.bin` с диска через `int 13h` `AH=0x02` и передаёт туда управление. Не часть самой BIOS. |
| `stage2.asm` / `stage2.bin` | Тестовый диск, stage 2: понятный человеку пошаговый прогон `int 10h`/`int 16h`/`int 13h` (грузится stage 1, в один сектор не влезает). `boot.bin` подключает его через `incbin` плюс ещё 2 сектора данных — запусти `make run` и читай экран. |
| `disklayout.inc` | Общие константы раскладки секторов (подключаются через `%include` и в `boot.asm`, и в `stage2.asm`), чтобы номера секторов не разъехались между файлами. |

## Сборка

```bash
make
```

`font.bin` должен лежать рядом с `sbios.asm` — он подключается на этапе
сборки через `incbin`, отдельно собирать/прикладывать не нужно.

## Запуск

```bash
# Без диска - POST, попытка загрузки завершится "No bootable disk found"
make run_nhda

# С тестовым загрузочным сектором
make run
```

POST заканчивается приглашением "Press DEL to enter SETUP..." — как у
настоящего BIOS: нажми Del в течение короткого окна после этого, чтобы
открыть setup-меню, иначе загрузка продолжится сама. В меню: стрелки
вверх/вниз — навигация, Enter — переключить тумблер (или открыть пункт,
для System Information, или выйти, на Exit), Esc — выйти и продолжить
обычную последовательность загрузки (попытку читать MBR с диска).
Настройки сохраняются в CMOS/NVRAM:

- **Serial (COM1) output** / **VGA output** — два исходных тумблера.
- **Boot device** — Master или Slave: с какого физического диска
  `ata_read_mbr` читает и какой `DL` передаётся загруженному коду (см.
  "Архитектурные заметки" — раньше эти два места могли разойтись, это
  была отдельная скрытая ошибка).
- **Quiet boot** — скрывает баннер/тест памяти/самотест клавиатуры на
  VGA (serial-вывод не затрагивается, у него свой отдельный тумблер).
  Ошибки не скрываются никогда, независимо от Quiet boot.
- **System Information** — экран только для просмотра: модель CPU
  (через "brand string" `CPUID`, с честным fallback на 12-байтный
  Vendor ID или "Unknown (no CPUID)" на всём достаточно старом, чтобы
  CPUID не поддерживать), conventional/extended память, текущий
  загрузочный диск, CHS-геометрия HDD/floppy. Любая клавиша возвращает
  в меню.

После Esc (или после того, как приглашение Del само истечёт) тестовый
диск печатает понятный, пошаговый рассказ о каждом вызове `int 10h`/
`int 16h`/`int 13h` (`stage2.asm`) — набери пару клавиш, когда попросит,
и читай строки `-> OK`, чтобы увидеть, что именно проверяется.

## Архитектурные заметки

Несколько неочевидных вещей, с которыми пришлось разобраться по ходу дела —
пригодится, если будешь читать/расширять исходник:

- **ROM — это не RAM.** `CS`/`DS` в загруженном образе указывают на сам
  ROM-образ (в реальном железе — Flash-память, доступная только на чтение).
  Все изменяемые переменные (курсор VGA, буфер под число, флаги тумблеров,
  индекс выбранного пункта меню и т.д.) поэтому вынесены в настоящую RAM —
  в свободную область сразу после IVT (`0x000`–`0x3FF`) и BDA (`0x400`–
  `0x4FF`), начиная с `0x500`, и адресуются через `ss:` (поскольку `SS`
  всегда указывает на сегмент `0x0000`).
- **Своей видео-BIOS у нас нет** — поэтому и переход в текстовый режим 80×25,
  и загрузка шрифта в Character Generator RAM (план 2 видеопамяти), и
  прошивка палитры DAC сделаны вручную, через прямое программирование
  регистров контроллера.
- **Контроллер клавиатуры нативно отдаёт Scan Code Set 2**, а не Set 1 —
  проверено эмпирически, не предполагалось "по документации". Раньше
  проект сам декодировал сырой Set 2 (учитывая код "отпускания" `F0 xx`
  и транслируя в Set 1 только для вывода `int 16h` в `AH`), но теперь
  вместо этого включает аппаратную трансляцию Set 2 → Set 1 у самого
  контроллера (бит6 Controller Configuration Byte — то же самое, что
  делает настоящий BIOS). Всё, что ниже — `kbd_service`, `setup_menu`,
  и любой загруженный код, читающий порт `0x60` напрямую — теперь видит
  обычный Set 1 (отпускание = код нажатия с битом7, один байт, а не
  отдельный префикс `F0`). Переключились после того, как реальная
  IRQ-driven ОС, как только заработала сама доставка IRQ, стала
  декодировать каждую клавишу неверно очень конкретным образом
  (`h` как `,`, `e` как `j`, ...) и с задвоением каждого нажатия — она
  читала сырой Set 2 с провода и интерпретировала его как Set 1, ровно
  наоборот тому, что делал сам проект. Подробности и почему это
  всплыло только сейчас — в записи про Local APIC LVT0 ниже, в разделе
  "Известные ограничения".
- **Собственный загрузочный код BIOS не может вызвать `int 13h`** — это
  как раз то, что BIOS предоставляет, а не то, чем она сама пользуется,
  поэтому чтение MBR (`ata_read_mbr`) всё так же напрямую через порты
  ATA-контроллера. А вот загруженный код (загрузчик, вторая стадия, ОС)
  может вызывать `int 13h`, как на настоящем железе.
- **Скрытая ошибка, которую сразу же вскрыло добавление пункта "Boot
  device" в setup**: `ata_read_mbr` всегда безусловно обращалась к
  master ATA, а `boot_try_disk` при этом передавала загруженному коду
  тот `DL`, который выбрали в setup-меню — то есть "Slave" мог
  прочитать MBR с master в память и затем передать туда управление,
  представившись slave-диском. Безобидно, пока селектор диска был
  зашит намертво (оба места всегда совпадали по построению),
  невозможно не заметить, как только это стало настройкой: попытка
  загрузиться со "Slave" при подключённом только master корректно
  завершилась "No bootable disk found" вместо тихой загрузки не того
  диска не под своим именем. Исправлено тем, что `ata_read_mbr`
  теперь тоже читает `RAM_BOOT_DRIVE` для выбора master/slave на порт
  `0x1F6` — то же самое значение, которое `boot_try_disk` сразу следом
  кладёт в `DL`.
- **`int 16h` `AH=0x01` и `int 13h` (`AH=0x00`/`0x02`/`0x08`) возвращают
  результат через флаг** (`ZF` / `CF`) — но `iret` восстанавливает `FLAGS`
  из того, что сам `int` запушил на стек при входе, а не из текущего
  регистра флагов. Поэтому обработчик патчит это слово на стеке напрямую
  прямо перед `iret` (общий вспомогательный `patch_stack_cf` делает это
  для всех трёх функций `int 13h`). Перепутать полярность здесь легко и
  незаметно — символы/данные декодируются правильно, а `jz`/`jnz`/`jc` у
  вызывающего кода видит противоположное состояние. Именно такой баг один
  раз уехал в код у `int 16h` и был пойман только сырым дампом
  регистров/флагов по serial, а не чтением исходника. `int 13h` писался
  уже с этим уроком в голове и был проверен так же, до того как
  доверять скриншоту.
- **Неподдерживаемые функции `int 13h` явно возвращают `CF=1`/`AH=1`** —
  в отличие от `int 10h`/`int 16h`, которые для всего непонятного молча
  ничего не делают. Для видео/клавиатуры молчание безопаснее; для
  дисковых операций тихо соврать об успехе там, где ничего не произошло,
  хуже честной ошибки — вызывающий код может начать работать с данными,
  которые на самом деле не прочитались.
- **Текст за последней строкой раньше просто пропадал.** Обработчик
  перевода строки в `vga_char_out` только вычислял смещение СЛЕДУЮЩЕЙ
  строки — ничто не мешало ему вычислить позицию за строкой 24 и писать
  туда же, за пределами видимого 4000-байтного текстового буфера.
  Безобидно, пока весь экран укладывался в 25 строк (POST, setup-меню);
  всплыло, как только более длинная тестовая программа напечатала больше
  — экран выглядел зависшим, хотя процессор продолжал исполнение как ни
  в чём не бывало (подтверждено цепочкой serial-чекпоинтов, которая
  показала, что выполнение спокойно доходит до конца, пока экран стоит
  замороженным). Исправлено через `vga_scroll_up`, которую путь записи
  вызывает, как только курсор собирается пересечь 25-ю строку: строки
  1-24 копируются в 0-23, освободившаяся строка 24 очищается.
- **Контроллер прерываний 8259 (PIC) переинициализируется (remap) во
  время POST**, как у любого настоящего PC/AT BIOS: master IRQ0-7 →
  `INT 0x08`-`0x0F`, slave IRQ8-15 → `INT 0x70`-`0x77`, с открытыми
  IRQ0/1/2. Сам проект прерывания никогда не включает (`IF` весь POST/
  setup остаётся выключенным — обрабатывать IRQ здесь некому), поэтому
  отсутствие этого шага было бы незаметно в любом собственном тесте
  проекта. Сначала показалось, что именно в этом всё дело — загруженная
  ОС со своим PS/2-драйвером клавиатуры перестала получать ввод именно
  под этим BIOS, при том что под настоящим всё работало — но у этой ОС
  оказался свой полный remap PIC, так что для этого конкретного бага
  состояние PIC роли не играло (настоящую причину см. в следующем
  пункте). Оставлено в проекте всё равно — это реально отсутствовавшее
  поведение настоящего BIOS, и какая-нибудь другая загруженная ОС вполне
  может на него полагаться.
- **Контроллер клавиатуры не поднимет IRQ1, пока ему явно не сказать.**
  Пройденный самотест (`0xAA`) — не то же самое, что включённая генерация
  прерываний: за это отвечает отдельный бит (бит0) в Controller
  Configuration Byte (команды `0x20`/`0x60` на порт `0x64`), а весь
  клавиатурный ввод в этом проекте — чистый поллинг, поэтому этот бит
  никогда и не требовался. Осталось незамеченным ровно до того момента,
  как загруженная ОС с полностью IRQ-driven драйвером клавиатуры (без
  какого-либо поллинга) стала получать ноль нажатий под этим BIOS, даже
  правильно настроив свои IDT и remap PIC — прерывание просто никогда не
  поднималось, ещё до уровня, который контролировала сама ОС. Исправлено
  чтением Configuration Byte сразу после успешного самотеста, установкой
  бита0 (разрешить IRQ1) и явным сбросом бита6 (аппаратная трансляция
  Set 2 → Set 1, которая должна оставаться выключенной — весь клавиатурный
  стек проекта зависит от сырого Set 2) перед записью обратно. Фикс
  настоящий и корректный, но — см. следующий пункт — оказалось, что это
  ещё не вся история для реальной доставки IRQ загруженной ОС.
- **Legacy-прерывания от PIC вообще не доходят до CPU, пока явно не
  снять маску со входа LINT0 у Local APIC — сверх правильно настроенных
  PIC и 8042 выше.** На любом CPU с Local APIC (то есть практически везде,
  где запустится этот BIOS, включая QEMU) IRQ от 8259 доходят до ядра
  именно через этот вход, а по Intel SDM он после RESET замаскирован по
  умолчанию. Настоящий BIOS всегда программирует его (регистр LVT LINT0,
  физический адрес `0xFEE00350`, режим доставки ExtINT) во время POST;
  подтверждено эмпирически на выделенном 32-битном multiboot-тестовом
  ядре — прерывания реально пошли ровно после записи в этот регистр.
  Проблема в том, что этот адрес недостижим из 16-битного реального
  режима, а значит фикс означает кратковременный вход в 32-битный режим
  прямо во время POST. Первая попытка через полный переход
  real→protected→real (со сменой `CS` через far `jmp`, а затем прыжком
  обратно) воспроизводимо зависала на обратном прыжке по причинам,
  которые не поддались ни дампам регистров, ни GDB-отладке, и была
  откачена, а не оставлена в полурабочем виде. Рабочая версия использует
  "unreal mode": вход в protected mode, загрузка ТОЛЬКО `ES` плоским
  дескриптором, выход обратно в реальный режим — `CS` вообще не
  трогается, поэтому и обратному прыжку неоткуда взяться и нечему
  сломаться. Ещё одна деталь, найденная так же - тестированием, а не
  предположением: у Local APIC есть отдельный бит "программного
  включения" в Spurious Interrupt Vector Register (`0xFEE000F0`) - без
  него даже корректно снятая маска на LVT LINT0 всё равно ничего не
  доставляет. А как только реальная доставка IRQ0/IRQ1 заработала,
  вскрылось ещё одно: любой загруженный код, который просто делает
  честный `sti` (стандартная практика для boot-секторов реального
  режима, включая собственный `boot.asm` этого проекта), ожидает, что
  настоящий BIOS уже поставил свои обработчики `INT 0x08`/`INT 0x09` -
  без них первый же тик таймера прыгает в произвольный мусор по этому
  адресу IVT. Исправлено добавлением минимальных версий обоих:
  `INT 0x08` считает стандартный тик-счётчик в BDA и шлёт `EOI`;
  `INT 0x09` просто вызывает уже существующую `kbd_service` (ту же,
  что опрашивает `int 16h`) напрямую - к моменту вызова ISR байт на
  порту `0x60` уже гарантированно есть, так что один и тот же путь
  декодирования обслуживает и поллинг, и IRQ-driven вызовы. Проверено
  выделенным real-mode тестом счётчика IRQ1 (корректно считает и
  нажатие, и отпускание), штатным регрессионным диском, меню GRUB и -
  после того как в самом ТЕСТОВОМ ядре нашёлся и исправился
  захардкоженный неверный селектор кодового сегмента (именно он, а не
  этот BIOS, был причиной его падения) - тем же 32-битным
  multiboot-ядром, которым изначально диагностировалась проблема. Как
  только реальная доставка IRQ заработала, в ту же сессию всплыла ещё
  одна, последняя проблема: реальная IRQ-driven ОС декодировала каждую
  клавишу неверно вполне конкретным, предсказуемым образом (`h` → `,`,
  `e` → `j`, каждое нажатие задваивалось) - см. запись про Scan Set 2
  vs Set 1 выше, в "Design notes", там же и фикс.
- **Дисковая функция, которая "успешно" возвращает не тот номер диска —
  хуже, чем честная ошибка.** `int13h_read_sectors` использовала `DX`
  как обычный scratch-регистр для адресов портов ATA и не восстанавливала
  его перед возвратом — вызывающий код получал обратно `DL=0xF0`
  (остаток от последней записи в порт) вместо своего же номера диска.
  Незаметно, пока никто строго не проверял `DL`; всплыло как настоящая
  регрессия — GRUB стал падать в `Read Error` — как только проверка
  номера диска в другом месте стала строже. Исправлено тем же приёмом
  `push dx`/`pop dx`, что уже был у `int13h_reset`.

## Известные ограничения

- Обработчик `int 10h` поддерживает `AH=0x0E`, `AH=0x00` (только режим
  `0x03`, остальные номера тихо игнорируются), `AH=0x02`/`0x03`, `AH=0x0F`
  и `AH=0x09`. Прочие видео-функции — в частности VESA/VBE (`AH=0x4F`,
  нужна для графических режимов с линейным framebuffer) — тихо
  игнорируются, из-за чего графическая ОС отпадает сразу (КолибриОС
  даже не пробовали запускать по этой же причине — ей как раз нужен VBE,
  а это разрыв побольше, чем всё, во что упирались текстовые DOS/GRUB).
- Обработчик `int 16h` поддерживает только `AH=0x00`/`0x01` и декодирует
  только основной алфавитно-цифровой блок (без numpad, функциональных и
  прочих не-ASCII клавиш). Расширенные (`E0`-префиксные) клавиши
  пропускаются, а не декодируются — из-за этого расширенная клавиша может
  случайно совпасть по коду с клавишей numpad; это осознанное упрощение, а
  не забытый баг.
- Обработчик `int 13h` поддерживает только `AH=0x00`/`0x02`/`0x08`,
  транслирует CHS в LBA по условной (не запрошенной у диска) геометрии,
  выбираемой только по номеру диска (`18/2` для `DL<0x80`, `63/16` для
  `DL>=0x80`), и не реализует `IDENTIFY DEVICE` — `AH=0x08` всегда
  репортит один и тот же условный максимум цилиндра вне зависимости от
  реального размера образа диска. Секторы читаются по одному, а не
  пачкой - проще и надёжнее, но медленнее.
- Настоящая дискета FreeDOS с исправлением геометрии `int 13h` грузится
  заметно дальше (её собственные чтения теперь попадают в нужные
  секторы), но до рабочего промпта всё равно не доходит — и, судя по
  временному логу вызовов, дело не в `int 12h`/`int 15h`: FreeDOS их
  вообще не вызывает. То, что она делает после последнего чтения через
  `int 13h`, — её собственная внутренняя логика, а не недостающий
  сервис BIOS; разобраться можно только дизассемблировав саму FreeDOS.
  GRUB (см. выше) оказался куда более полезным тестовым случаем — его
  сообщения об ошибках прямо называли недостающую деталь каждый раз,
  вместо молчаливого зависания.
- Загрузка с диска самой BIOS (чтение MBR) умеет только сектор LBA0, без
  работы с разделами.
- Клавиатура читается поллингом, без IRQ/PIC — годится для setup-меню, но
  не годится для полноценной многозадачной ОС.
- Debug Key / подпись HWID — рассматривались, но осознанно не добавлены:
  проект open source, а жёсткий гейтинг фич через встроенный секрет
  технически несовместим с открытыми исходниками (секрет всё равно можно
  вытащить дизассемблером).
