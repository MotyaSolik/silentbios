# SilentBIOS

Вайбкод хрень by Claude

Самодельный минимальный BIOS для x86 (16-бит real mode), написанный с нуля на
NASM-ассемблере. Занимает ровно 64 КБ и размещается как обычный legacy BIOS
ROM-образ — reset vector в конце файла делает `jmp` на точку входа, как на
настоящей материнской плате.

Собирался и проверялся в QEMU (`qemu-system-i386`) на каждом шаге — не
просто "компилируется", а реально гонялся с осмотром serial-вывода и
скриншотов VGA-экрана.

## Возможности

- **Вывод по COM1** (9600 8N1) — простейший, но независимый от видео канал
  диагностики.
- **VGA text mode 80×25**, настроенный полностью вручную через порты
  контроллера (Sequencer, CRTC, Graphics Controller, Attribute Controller,
  DAC-палитра) — без какой-либо видео-BIOS/option ROM. Растровый шрифт 8×16
  сгенерирован и зашит отдельным бинарником (`font.bin`, подключается через
  `incbin`). Вывод за последней строкой прокручивает экран вверх, а не
  утекает за пределы видимого буфера.
- **POST-диагностика**: тест conventional-памяти (0–640 КБ, блоками по 64 КБ)
  и самотест контроллера клавиатуры 8042 (команда `0xAA`).
- **Интерактивное setup-меню** — стрелки/Enter/Esc, опрос клавиатуры прямым
  поллингом портов `0x60`/`0x64` (Scan Code Set 2, с фильтрацией
  make/break-кодов). Тумблеры Serial/VGA output реально встроены в вывод, а
  не просто рисуются.
- **CMOS/NVRAM** — настройки тумблеров сохраняются в CMOS (порты `0x70`/
  `0x71`) и переживают аппаратный reset, как на настоящей материнке с
  батарейкой.
- **Загрузка с диска** — чтение MBR (сектор LBA0) напрямую с первичного ATA-
  контроллера в режиме PIO (порты `0x1F0`–`0x1F7`), проверка сигнатуры
  `0x55AA` и передача управления по адресу `0000:7C00` с регистрами,
  выставленными как у настоящего BIOS (`DS=ES=SS=0`, `SP=0x7C00`,
  `DL=0x80`).
- **`int 10h`** — настоящий обработчик программного прерывания, прописанный
  в IVT. Загруженный код/ОС может просто вызывать `int 10h`, как в настоящем
  BIOS, вместо прямого доступа к видеопамяти/портам. Поддержанные функции:
  `AH=0x0E` (teletype output), `AH=0x00` (смена режима — только `0x03`),
  `AH=0x02`/`0x03` (установка/чтение позиции курсора, включая настоящий
  аппаратный курсор CRTC через порты `0x3D4`/`0x3D5`), `AH=0x0F` (чтение
  режима), `AH=0x09` (запись символа с атрибутом без сдвига курсора —
  добавлена, потому что именно ею GRUB рисует цветную рамку меню; без
  неё GRUB работал, но ничего не рисовал).
- **`int 16h`** (клавиатурные сервисы) — декодирует тот же сырой поллинг
  Scan Set 2, что и setup-меню, в ASCII, с поддержкой Shift. `AH=0x00`
  читает символ (блокирующе), `AH=0x01` проверяет наличие клавиши, не
  потребляя её (неблокирующе, результат через `ZF`). Numpad, функциональные
  и прочие не-ASCII клавиши тихо игнорируются.
- **`int 13h`** (дисковые сервисы) — загруженный загрузчик/ОС может читать
  диск, не разговаривая с ATA-контроллером напрямую. `AH=0x00` (сброс),
  `AH=0x02` (чтение секторов, CHS — транслируется в LBA28 по условной
  геометрии, т.к. `IDENTIFY DEVICE` не реализован), `AH=0x08` (параметры
  диска). Геометрия зависит от номера диска: `DL<0x80` (floppy) →
  `18 секторов/дорожка, 2 головки` (стандарт 1.44MB), `DL>=0x80` (HDD) →
  `63/16` — найдено эмпирически, попыткой загрузить настоящую дискету
  FreeDOS и временным serial-логом каждого вызова `int 13h`, чтобы
  увидеть, какие именно CHS запрашивает её загрузочный сектор. Об
  ошибках сообщает честно: неподдерживаемая функция возвращает
  `CF=1`/`AH=1`, а не тихо притворяется, что всё прошло успешно — для
  дисковых операций так безопаснее, чем для видео/клавиатуры.
- **`int 12h`** (объём conventional-памяти) и **`int 15h` `AH=0x88`**
  (объём расширенной памяти). `int 12h` возвращает то, что реально
  измерил `post_memory_test` при POST (0-640KB). `int 15h AH=0x88`
  берёт ответ прямо из стандартных CMOS-ячеек `0x17`/`0x18` (расширенная
  память в KB), которые заполняет сама платформа — как настоящее
  железо, так и QEMU; сами память выше 1MB мы не пробуем (нет
  A20-gate/unreal mode). Прочие функции `int 15h` возвращают
  `CF=1`/`AH=0x86` ("функция не поддерживается") — тот же код, что и у
  настоящего BIOS в этом случае.

## Запускает GRUB

Настоящий образ GRUB (собранный `grub-mkrescue`) доходит до
интерактивного промпта `grub rescue>` на этой BIOS — набранные команды
реально печатаются на экране, как на настоящем железе. (Файловая
система там показывается как "unknown" — потому что тестовый образ
это ISO9660-раскладка для CD, скормленная как сырой диск, это
особенность тестового образа, а не ограничение BIOS.) До этого
результата привели три находки, каждая — по чтению точного текста
ошибки: разделение геометрии floppy/HDD у `int 13h`, `int 10h AH=0x09`
для рамки меню GRUB, и настоящие числа в `int 15h AH=0x88` вместо
честного нуля.

## Структура файлов

| Файл             | Назначение                                                        |
|-------------------|--------------------------------------------------------------------|
| `bios.asm`        | Исходник BIOS                                                      |
| `font.bin`        | Растровый шрифт 8×16 (256 символов × 16 байт), подключается через `incbin` |
| `sbios.bin`       | Готовый собранный образ, 65536 байт                                |
| `boot.asm` / `boot.bin` | Тестовый диск, stage 1: сектор MBR. Минимальный загрузчик — печатает строку, читает `stage2.bin` с диска через `int 13h` `AH=0x02` и передаёт туда управление. Не часть самой BIOS. |
| `stage2.asm` / `stage2.bin` | Тестовый диск, stage 2: понятный человеку пошаговый прогон `int 10h`/`int 16h`/`int 13h` (грузится stage 1, в один сектор не влезает). `boot.bin` подключает его через `incbin` плюс ещё 2 сектора данных — запусти `make run` и читай экран. |
| `disklayout.inc` | Общие константы раскладки секторов (подключаются через `%include` и в `boot.asm`, и в `stage2.asm`), чтобы номера секторов не разъехались между файлами. |

## Сборка

```bash
make
```

`font.bin` должен лежать рядом с `sbios.asm` — он подключается на этапе
сборки через `incbin`, отдельно собирать/прикладывать не нужно.

## Запуск

```bash
# Без диска - POST, VGA, меню, попытка загрузки завершится "No bootable disk found"
make run_nhda

# С тестовым загрузочным сектором
make run
```

В setup-меню: стрелки вверх/вниз — навигация, Enter — переключить тумблер
или выбрать пункт, Esc — выйти и продолжить обычную последовательность
загрузки (попытку читать MBR с диска).

После Esc `make run` грузит тестовый диск, который печатает понятный,
пошаговый рассказ о каждом вызове `int 10h`/`int 16h`/`int 13h`
(`stage2.asm`) — набери пару клавиш, когда попросит, и читай строки
`-> OK`, чтобы увидеть, что именно проверяется.

## Архитектурные заметки

Несколько неочевидных вещей, с которыми пришлось разобраться по ходу дела —
пригодится, если будешь читать/расширять исходник:

- **ROM — это не RAM.** `CS`/`DS` в загруженном образе указывают на сам
  ROM-образ (в реальном железе — Flash-память, доступная только на чтение).
  Все изменяемые переменные (курсор VGA, буфер под число, флаги тумблеров,
  индекс выбранного пункта меню и т.д.) поэтому вынесены в настоящую RAM —
  в свободную область сразу после IVT (`0x000`–`0x3FF`) и BDA (`0x400`–
  `0x4FF`), начиная с `0x500`, и адресуются через `ss:` (поскольку `SS`
  всегда указывает на сегмент `0x0000`).
- **Своей видео-BIOS у нас нет** — поэтому и переход в текстовый режим 80×25,
  и загрузка шрифта в Character Generator RAM (план 2 видеопамяти), и
  прошивка палитры DAC сделаны вручную, через прямое программирование
  регистров контроллера.
- **Контроллер клавиатуры отдаёт Scan Code Set 2**, а не Set 1 — это
  проверено эмпирически (не предполагалось "по документации"), и код
  обработки клавиш учитывает и это, и то, что код "отпускания" клавиши
  (`F0 xx`) оканчивается тем же байтом, что и код нажатия.
- **Собственный загрузочный код BIOS не может вызвать `int 13h`** — это
  как раз то, что BIOS предоставляет, а не то, чем она сама пользуется,
  поэтому чтение MBR (`ata_read_mbr`) всё так же напрямую через порты
  ATA-контроллера. А вот загруженный код (загрузчик, вторая стадия, ОС)
  может вызывать `int 13h`, как на настоящем железе.
- **`int 16h` `AH=0x01` и `int 13h` (`AH=0x00`/`0x02`/`0x08`) возвращают
  результат через флаг** (`ZF` / `CF`) — но `iret` восстанавливает `FLAGS`
  из того, что сам `int` запушил на стек при входе, а не из текущего
  регистра флагов. Поэтому обработчик патчит это слово на стеке напрямую
  прямо перед `iret` (общий вспомогательный `patch_stack_cf` делает это
  для всех трёх функций `int 13h`). Перепутать полярность здесь легко и
  незаметно — символы/данные декодируются правильно, а `jz`/`jnz`/`jc` у
  вызывающего кода видит противоположное состояние. Именно такой баг один
  раз уехал в код у `int 16h` и был пойман только сырым дампом
  регистров/флагов по serial, а не чтением исходника. `int 13h` писался
  уже с этим уроком в голове и был проверен так же, до того как
  доверять скриншоту.
- **Неподдерживаемые функции `int 13h` явно возвращают `CF=1`/`AH=1`** —
  в отличие от `int 10h`/`int 16h`, которые для всего непонятного молча
  ничего не делают. Для видео/клавиатуры молчание безопаснее; для
  дисковых операций тихо соврать об успехе там, где ничего не произошло,
  хуже честной ошибки — вызывающий код может начать работать с данными,
  которые на самом деле не прочитались.
- **Текст за последней строкой раньше просто пропадал.** Обработчик
  перевода строки в `vga_char_out` только вычислял смещение СЛЕДУЮЩЕЙ
  строки — ничто не мешало ему вычислить позицию за строкой 24 и писать
  туда же, за пределами видимого 4000-байтного текстового буфера.
  Безобидно, пока весь экран укладывался в 25 строк (POST, setup-меню);
  всплыло, как только более длинная тестовая программа напечатала больше
  — экран выглядел зависшим, хотя процессор продолжал исполнение как ни
  в чём не бывало (подтверждено цепочкой serial-чекпоинтов, которая
  показала, что выполнение спокойно доходит до конца, пока экран стоит
  замороженным). Исправлено через `vga_scroll_up`, которую путь записи
  вызывает, как только курсор собирается пересечь 25-ю строку: строки
  1-24 копируются в 0-23, освободившаяся строка 24 очищается.

## Известные ограничения

- Обработчик `int 10h` поддерживает `AH=0x0E`, `AH=0x00` (только режим
  `0x03`, остальные номера тихо игнорируются), `AH=0x02`/`0x03`, `AH=0x0F`
  и `AH=0x09`. Прочие видео-функции — в частности VESA/VBE (`AH=0x4F`,
  нужна для графических режимов с линейным framebuffer) — тихо
  игнорируются, из-за чего графическая ОС отпадает сразу (КолибриОС
  даже не пробовали запускать по этой же причине — ей как раз нужен VBE,
  а это разрыв побольше, чем всё, во что упирались текстовые DOS/GRUB).
- Обработчик `int 16h` поддерживает только `AH=0x00`/`0x01` и декодирует
  только основной алфавитно-цифровой блок (без numpad, функциональных и
  прочих не-ASCII клавиш). Расширенные (`E0`-префиксные) клавиши
  пропускаются, а не декодируются — из-за этого расширенная клавиша может
  случайно совпасть по коду с клавишей numpad; это осознанное упрощение, а
  не забытый баг.
- Обработчик `int 13h` поддерживает только `AH=0x00`/`0x02`/`0x08`,
  транслирует CHS в LBA по условной (не запрошенной у диска) геометрии,
  выбираемой только по номеру диска (`18/2` для `DL<0x80`, `63/16` для
  `DL>=0x80`), и не реализует `IDENTIFY DEVICE` — `AH=0x08` всегда
  репортит один и тот же условный максимум цилиндра вне зависимости от
  реального размера образа диска. Секторы читаются по одному, а не
  пачкой - проще и надёжнее, но медленнее.
- Настоящая дискета FreeDOS с исправлением геометрии `int 13h` грузится
  заметно дальше (её собственные чтения теперь попадают в нужные
  секторы), но до рабочего промпта всё равно не доходит — и, судя по
  временному логу вызовов, дело не в `int 12h`/`int 15h`: FreeDOS их
  вообще не вызывает. То, что она делает после последнего чтения через
  `int 13h`, — её собственная внутренняя логика, а не недостающий
  сервис BIOS; разобраться можно только дизассемблировав саму FreeDOS.
  GRUB (см. выше) оказался куда более полезным тестовым случаем — его
  сообщения об ошибках прямо называли недостающую деталь каждый раз,
  вместо молчаливого зависания.
- Загрузка с диска самой BIOS (чтение MBR) умеет только сектор LBA0, без
  работы с разделами.
- Клавиатура читается поллингом, без IRQ/PIC — годится для setup-меню, но
  не годится для полноценной многозадачной ОС.
- Debug Key / подпись HWID — рассматривались, но осознанно не добавлены:
  проект open source, а жёсткий гейтинг фич через встроенный секрет
  технически несовместим с открытыми исходниками (секрет всё равно можно
  вытащить дизассемблером).
